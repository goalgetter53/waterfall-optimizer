# Real-world calibration: sources and assumptions

All sources were accessed on **2026-11-20**. The machine-readable version is
[`configs/real_calibrated.json`](../configs/real_calibrated.json). Every number in it is a
`{"value", "source"}` pair, where `source` is a key in the table below or the literal
`ASSUMPTION` with a note. `tests/test_calibration.py` checks that rule. The file is
regenerated by `make calibrate-real` (`scripts/derive_real_calibration.py`), which downloads
the two benchmark CSVs and recomputes every rate.

**What this calibration is and is not.** Prices are public **list prices** for the cheapest
self-serve paid plan, not negotiated contract prices. Hit and accuracy rates come from
**benchmarks run by vendors that took part in their own tests**. Contacts and provider
outcomes in the simulator are still **simulated**. No live vendor traffic was used, because
this environment has no vendor API keys.

Notes:

- USD per successful find = plan price / included credits, at one credit per email. All four
  vendors publish a pay-on-found rule, so `charge_on_miss = false` for every provider. That
  differs from the illustrative world, where three of the four charged on misses.
- The headline run uses the published monthly-billing price where one exists. Apollo publishes
  only an annual-billing price, so Apollo is slightly favoured. The sensitivity sweep includes
  an **annual-billing price set** for all four.
- Optional vendors (Snov.io, Findymail, Kaspr, Lusha) were **not used**. Their pricing pages
  were fetched, but the simulator models four providers, and the Findymail page did not show
  an unambiguous cheapest tier.
- How the pages were read: Hunter's and Dropcontact's pricing pages are server-rendered and
  were read with a plain HTTPS GET. Apollo's and Prospeo's prices are rendered by JavaScript,
  so they were read with a JS-rendering scraper (Firecrawl) on the live page. The ECB rate
  came from the ECB daily XML feed.

**How the world model is fitted (moment matching).** The simulator's generative model is
unchanged (see `src/wfo/sim/world.py`). A contact is "discoverable" with probability d. A
provider returns an email with probability h if the contact is discoverable, or
0.15·h (a wrong guess) if it is not. A returned email is correct with probability a, and the
verifier rates a correct email valid 97% of the time and a wrong one 1% of the time. Given d,
each provider's (h, a) is solved so the model reproduces that provider's found and valid
rates **exactly**. d itself (**0.858**) is solved by bisection so that the model's
P(at least one of the 4 is valid) equals the observed 85.3%. That builds in the observed
"nobody can find this person" correlation. Beyond that shared latent, providers are
independent; real vendors share sources more than that.

**Segment-level effects.**

- **Country (real data, small samples).** From `S_amf`, contacts are split by domain ccTLD:
  .uk (n=156), .de (n=100), .fr (n=107). Everything else (n=4,637, mostly .com) is a **US
  proxy**. Each provider's country modifier is logit(h_country) − logit(h). For **IN**, the
  OrbiSearch APAC-vs-overall ratio (n=94 vs 288) is used for Apollo, Hunter and Prospeo, and
  the Dropcontact IN modifier is an **assumption (0)**. At n≈100, a country rate has a 95%
  interval of roughly ±9 pp. The sweep therefore includes a "no country effects" variant.
- **Company size and seniority: no public data found → ASSUMPTION** that the modifiers are 0.
  The only size/seniority variation is the repo's per-seed segment noise (logit SD 0.35),
  which is swept over 0, 0.35 and 0.7.

## 3. Everything that is still an assumption

| Item | Value | Why |
|---|---|---|
| Unresolvable catch-all rate | 0 | The benchmark's "valid" label already adjudicates catch-alls (BounceBan), so they are netted into the valid rates |
| Verification cost per found email | $0.00 | All four vendors bundle verification into the find credit (Hunter auto-verifies; Apollo charges only for verifiable emails; Prospeo sells verified emails; Dropcontact includes validation). An external verifier would add cost |
| Size and seniority modifiers | 0 | No public segment-level benchmark found |
| Segment noise | 0.35 (swept 0 to 0.7) | Repo default |
| Country / size / seniority mix | 40/15/15/10/20, 45/35/20, 55/30/15 | Repo default; no public B2B list mix was used |
| Latency, 5xx and 429 rates | Repo defaults per provider | No published numbers. They affect p95 latency, not cost |
| Verifier error model (97% / 93% / 6% / 1%) | Repo defaults | Model structure, unchanged |
| Value of a verified email V | $0.50 | Repo default (it drives the stopping rule) |

## 4. Sources that could not be used

- `https://www.findymail.com/pricing/` returned HTTP 403 to a plain GET. The JS-rendering
  scraper reached it, but the cheapest tier was ambiguous, so Findymail was not used.
- `https://orbisearch.com/research/email-finder-benchmark` returned HTTP 403 to a plain GET.
  The page was read through a search-engine excerpt, and its **CSV** downloaded fine and is
  what the calibration uses.
- No independent (non-vendor) benchmark with per-contact data was found. Every hit-rate
  source above is vendor-published.
